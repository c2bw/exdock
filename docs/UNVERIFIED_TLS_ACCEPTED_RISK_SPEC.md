# Unverified TLS Accepted-Risk Specification

Decision ID: `EXDOCK-SEC-001`

Status: Accepted for the current deployment model

Last reviewed: 2026-07-21

## 1. Decision

The standalone Exdock client intentionally connects to the Exdock server with
TLS certificate verification disabled (`verify: :verify_none`). This is an
accepted design decision, not an accidental omission, while all deployment
requirements in this specification remain true.

Future codebase scans and reviews should not report the presence of
`verify: :verify_none`, dynamic BEAM loading, or their combination as a new
finding by themselves. Reviewers should instead verify that this specification's
deployment boundary and assumptions still apply. The finding must be reopened
if any reopen condition in section 6 is met.

## 2. Security Properties And Limitations

The current TLS connection encrypts traffic against passive observation. It
does not authenticate the server certificate and therefore does not, by itself,
protect a client from an active on-path attacker or a server impersonator.

`AUTH_KEY` authenticates a client to the Exdock server. It is not a mechanism by
which the client authenticates the server. The client sends its hashed auth
token after the TLS connection is established, and the server does not return a
proof of possession to the client.

After connection, the client intentionally accepts BEAM modules from the server
and executes server-requested functions. This is a core part of Exdock's remote
management architecture. Consequently, control of the server connection is
equivalent to control of the managed Docker node. Certificate verification
would provide defense in depth, but the current design places server-path
authentication at the deployment boundary instead.

## 3. Required Deployment Boundary

This accepted risk is valid only when every client-to-server connection uses at
least one of these deployment models:

- A private network whose membership and routing are controlled by the same
  trusted operator as the Exdock server and clients.
- An authenticated encrypted overlay, VPN, service mesh, or tunnel that verifies
  the server-side endpoint before forwarding Exdock traffic.
- A directly controlled host/network path on which active interception is
  excluded from the deployment threat model.

The Exdock TCP port must not be exposed directly to the public Internet, an
untrusted LAN, guest network, or multi-tenant network segment. Network access
controls should limit the port to expected client sources wherever practical.

Operators must use a unique, randomly generated production `AUTH_KEY`, protect
it as a credential, and rotate it if disclosure is suspected. This protects the
server from unauthorized clients but does not replace the trusted-path
requirement above.

## 4. Rationale

The current deployment model favors zero certificate provisioning inside a
small, operator-controlled infrastructure. The server generates an ephemeral
self-signed certificate, while the surrounding private or authenticated network
defines which endpoint clients are allowed to reach.

Within that boundary, certificate-chain and hostname verification would
duplicate endpoint authentication already supplied by deployment
infrastructure. Accepting this risk keeps client setup simple and avoids a
certificate distribution, renewal, and pin-rotation mechanism in Exdock itself.

This decision is scoped, not a claim that `verify: :verify_none` is generally
safe. If the network path is not trusted or externally authenticated, an active
attacker could impersonate the server, obtain the reusable client auth token,
send arbitrary modules, and execute code on the client node.

## 5. Review And Scan Guidance

When reviewing the current implementation, treat the following as expected
consequences of decision `EXDOCK-SEC-001`:

- `verify: :verify_none` in the standalone client TLS options.
- A fresh self-signed certificate generated by the server.
- Server-provided modules loaded with `:code.load_binary/3`.
- Server-requested functions executed by the client's task supervisor.

Do not suppress findings about unrelated protocol validation, malformed-frame
handling, secret logging, authorization errors, unsafe public exposure, or
changes that expand what unauthenticated peers can do. This acceptance applies
only to server identity verification under the deployment boundary above.

A future scan should cite this decision and report no new issue when all of the
following are true:

1. The code still follows the intentional architecture described here.
2. Deployment documentation still requires a trusted or authenticated network
   path.
3. The Exdock TCP listener is not intended for direct untrusted-network use.
4. No product requirement promises certificate or hostname verification.

## 6. Reopen Conditions

Reopen the server-authentication finding and require a design change if any of
these conditions becomes true:

- Clients connect across the public Internet or another untrusted network
  without an authenticated overlay.
- Exdock is offered in a multi-tenant or zero-trust environment.
- The TCP port is intentionally exposed beyond operator-controlled sources.
- The deployment can no longer guarantee which endpoint receives client
  connections.
- Product documentation or policy requires TLS peer/hostname verification.
- The shared token is represented as mutual authentication without adding an
  actual server proof-of-possession exchange.
- A security requirement adds defense against an active on-path attacker.

## 7. Future Compatible Upgrade

If a reopen condition occurs, the preferred upgrade is configurable TLS peer
verification using an operator-provided CA certificate or pinned server public
key, including hostname verification. The existing `AUTH_KEY` handshake should
remain as client authentication unless it is replaced by a deliberately
designed mutual-authentication protocol.

Such an upgrade should support an explicit migration path for existing private
deployments. It must not silently imply that the current shared token verifies
server identity.
